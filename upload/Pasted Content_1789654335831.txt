# 3. CRITICAL SECURITY FIXES

## 3.1 AUTH_SECRET

Current problem:

The application has a hardcoded fallback similar to:

AUTH_SECRET = process.env.AUTH_SECRET || "lakhirad-dev-secret-change-in-production"

REMOVE this insecure fallback.

Production authentication MUST fail safely if AUTH_SECRET is missing.

Requirements:

* Require AUTH_SECRET in production.
* Use a cryptographically secure random secret.
* Never commit the secret to source control.
* Never expose AUTH_SECRET to frontend code.
* Add/update .env.example with:

AUTH_SECRET=

but NEVER put a real production secret there.

Add startup validation.

If NODE_ENV=production and AUTH_SECRET is missing:

* fail startup with a clear configuration error.

Do NOT silently use a default secret.

# 4. PASSWORD SECURITY

Current problem:

The application uses SHA-256 + salt for password hashing.

Replace password hashing with a password-specific hashing algorithm.

Preferred:

* Argon2id

Acceptable fallback:

* bcrypt with an appropriate cost factor.

Requirements:

* Never store plaintext passwords.
* Never log passwords.
* Never return password hashes through API responses.
* Never return salts to clients.
* Existing users must not be broken.

Implement a migration strategy.

Recommended approach:

1. Existing SHA-256 passwords remain temporarily supported.
2. When an existing user successfully logs in:

   * verify the legacy hash
   * immediately rehash the password using Argon2id/bcrypt
   * store the new password hash
   * mark the hashing version if necessary.
3. New passwords must always use Argon2id/bcrypt.
4. Provide an optional administrative migration mechanism if required.
5. Eventually remove legacy SHA-256 authentication after all accounts are migrated.

Use constant-time comparisons where appropriate.
